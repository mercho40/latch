# Architecture

How the macOS app, the iOS app and `latch-server` are put together. The target multi-device design is in the [roadmap](roadmap.md); running the server is in [Running latch-server](server.md).

## ACP mapping

Latch should preserve ACP semantics rather than inventing a second agent abstraction prematurely:

- `session/list` → session list
- `session/new` → new session
- `session/load` / `session/resume` → open session
- `session/list` → Resume Conversation…: a new session takes up one of the agent's own conversations in its folder, and shows the history the agent replays for it, which only the agent had
- `_session/steering` → a message sent while the agent works goes into its turn, for an agent whose `initialize` reply says `_meta.steering.supported`, as Claude Code's does. Latch asks with `idleBehavior: promptRequired`, so one that finds the turn over comes back to it and goes as a prompt of its own
- `session/fork` → Fork Session copies the conversation: the agent's fork under a new ID, which a new session with a copy of the transcript loads; with an agent that cannot fork, Fork Session opens an empty sibling
- `session/prompt` → send message: text, plus an `image` block for each attached image when the agent's `promptCapabilities.image` allows it, and a `resource_link` for each attached file or folder, or for an image the agent cannot take
- `session/cancel` → stop action
- `session/set_mode` → permission mode
- ACP updates → streamed messages and tool state; `available_commands_update` → the composer's `/` menu; `agent_thought_chunk` → folded Thinking rows; `plan` → the plan over the composer
- Subagents → the row of the call that runs one holds its calls, words and thinking, folded with it. Claude Code marks them with `_meta.claudeCode.parentToolUseId`, and forwards a subagent's words and thinking because Latch says it shows them (`_meta["subagent-transcript"]` in its client capabilities)
- ACP permission request → native approval sheet: the agent's own heading and reason, a plan to approve rendered as Markdown (Claude Code's ExitPlanMode), and each choice under Latch's trusted label, with the agent's words for it beside the label, never in its place
- ACP `elicitation/create` (form) → a question sheet: Claude Code asks its AskUserQuestion questions this way, and only of a client that says it answers forms (`elicitation.form`, which Latch does). Questions are brokered like permission requests, as `elicitationRequested`/`elicitationClosed` events and a `resolveElicitation` command, end when their turn does, and are refused when they ask for a page to open

A thin internal adapter can isolate ACP version changes and allow other structured harness adapters later.

## Embedded XPC service

The Xcode project builds two targets. `Latch` is the application; `LatchAgentXPCService` (bundle ID `dev.latchapp.mac.agent`) is an XPC service embedded in `Latch.app/Contents/XPCServices` that hosts one `LatchAgentService` for every session in the app. The app talks to it through `LatchAgentXPCClient`, one connection per session, and the service answers through `LatchAgentXPCHost`, which admits only same-user peers whose code signature satisfies `identifier "dev.latchapp.mac"`. All commands, streamed updates, and brokered permission requests cross that boundary; the UI never touches a runtime in-process. Disconnect stops only that session's runtime because the service is shared. If the connection is interrupted or invalidated, the session is shown as disconnected and a fresh connection is opened for the next attempt; nothing is replayed.

The embedded service sets `XPCService:JoinExistingSession`, so it shares the app's security session. Without it the service gets its own session, every keychain read from an agent fails with `errSecInteractionNotAllowed`, and agents that store provider credentials in the keychain — Claude Code among them — report a false "not signed in" on the first prompt even though their CLI is logged in. The service entry point lives in the `LatchAgentServiceHost` library of the app package so the same code can be unit-tested from SwiftPM. Both bundles are ad-hoc signed with hardened runtime and no sandbox. The SwiftPM preview (`swift run … Latch`) has no bundle and therefore hosts the service in-process; the bundled app does the same only when `LATCH_IN_PROCESS_AGENT=1` is set. The smoke test prints which transport it used and the service PID, and `Scripts/test-mac-app.sh` fails unless a separate service process handled it. Agent processes are children of the service, each leading its own process group; stopping a runtime signals the whole group, so a tool child the agent started goes with it. The app stops every local runtime before it quits (remote sessions detach instead; see [Remote sessions in the app](#remote-sessions-in-the-app)), but if the app or service is killed outright, nothing is left to send those signals and running agents are not cleaned up. A Mach-service launch agent via `SMAppService` remains pending.

## Failures and authentication

Agent RPC failures retain bounded, redacted display text across XPC instead of becoming a generic command failure. Arbitrary error metadata, stderr, and native error details are not forwarded as display text; redaction of free-form agent prose is best effort. ACP authentication-required errors stop the affected session and show sign-in/reconnection guidance, rather than leaving a potentially stale authenticated session ready. Reconnect explicitly by selecting the harness after signing in; prompts are never automatically replayed. Existing chat remains visible until a new session connects.

## Permission requests

Permission requests during the active prompt appear in native sheets with selectable, scrollable agent-provided request details. Only explicitly offered, known ACP option kinds can be selected. Return and Escape cancel the request; approval has no default shortcut. “Always” uses the agent's scope, not a saved Latch preference. Pending decisions are cancelled on prompt completion, Stop, agent disconnection or exit, or quit; stale sheet callbacks cannot approve a different request. Requests outside the active session/prompt, duplicate option IDs, and requests beyond the 16-decision queue limit are cancelled. A remote session differs in two ways: quitting takes its sheets down without answering, leaving the requests pending on the server, and every client following a runtime sees its requests. A session that is idle when another client prompts the runtime follows that turn, so it shows the turn's requests too, and the first answer to reach the server counts; the other client's sheet closes when the request does. A request raised while a session runs no turn at all belongs to another client, so it is left for that client rather than refused. These controls are not a sandbox guarantee; agents must still enforce their own restrictions. Permission requests are brokered by the service: the runtime registry holds the agent's request, publishes it as a `permissionRequested` event with a Latch-local request ID, and the client answers with a `resolvePermission` command. Pending requests are closed with a `permissionClosed` event when answered, and cancelled when the prompt ends, is cancelled, or the runtime stops or exits; at most 16 requests may wait per runtime. Because no client touches the in-process runtime directly, the same UI can later run against an XPC-hosted service. Real-provider approval flows have not yet been validated.

## Model, effort, and mode

Model, Effort, and Permission Mode pop-ups inside the composer use the connected agent's advertised ACP `configOptions` (categories `model`, `thought_level`, and `mode`, including grouped choices), with legacy `models` / `session/set_model` and `modes` / `session/set_mode` support when needed. No model names, effort levels, or permission modes are hard-coded. Mode names and descriptions belong to the harness: a mode may affect planning or tool approval policy and is not a Latch sandbox or automatic approval of pending requests. Changing a setting refreshes the advertised option set; unsupported settings are hidden. Picks are confirmed by the agent, errors keep the last confirmed selection, and controls are disabled during prompts or pending changes. Configuration is session-local, follows ordered agent updates, and is cleared on disconnect. Mock tests cover these paths; real-provider model/effort/mode switching has not yet been validated.

## Streaming and history

Streaming history keeps incremental character counts while preserving Unicode grapheme boundaries and the existing retention limits. Text-only UI rendering is coalesced with a one-shot 16 ms delay; permission, configuration, cancellation, and connection-state updates remain immediate. Persistence reads current history, not a delayed render snapshot. Streamed text does not refresh the sidebar, attention state, pickers, or composer layout.

## Service layer

The service layer now has these small primitives:

- `ACPAgentRuntime` owns one ACP subprocess and connection, forwards session updates and stderr, enforces lifecycle state, and reports unexpected process termination.
- `AgentRuntimeRegistry` reserves stable Latch-local IDs, prevents duplicate launches, supervises multiple runtimes, exposes Codable status snapshots and an outbound event stream, evicts terminated processes, and supports individual or concurrent shutdown.
- `LatchServiceProtocol` defines shared Codable commands, responses, events, launch profiles, and versioned request/reply/event envelopes used across the macOS service and native clients.
- `LatchAgentService` dispatches those transport-neutral commands, including permission resolutions, onto the runtime registry and exposes its single outbound event stream.
- `LatchServiceCodec` checks JSON payload byte limits before decoding and after encoding. The limit is 8 MB, the same as the largest frame the ACP connection accepts, so a prompt carrying several resized screenshots crosses the boundary whole.
- `LatchAgentXPC` (a macOS-only target in `LatchAgentCore`) adapts bounded `Data` requests to versioned service replies. Codec failures use sanitized transport errors; command failures remain in correlated replies.
- `LatchAgentXPCEventHub` consumes the service event stream once and broadcasts versioned, sequenced events to attached clients. Each client acknowledges delivery, with one event in flight and a configurable per-client queue limit (128 events including the in-flight event by default). Slow clients are disconnected; an unencodable event disconnects all current recipients rather than silently skipping it.

Start one event hub at service startup. After authorizing a peer, configure its request adapter and transfer the unresumed connection to `attach`; the hub installs its remote event interface and lifecycle handlers, then resumes it. Clients export `LatchAgentXPCEventReceiver` using the hub's interface. The host must explicitly shut down the hub before releasing it.

Events go to clients attached when the hub consumes them; upstream buffered events may predate attachment. The XPC path has no replay API; the network transport's replay hub, below, is separate. Per-client queues are bounded, but the upstream service stream is not. Shutdown or source completion aborts pending delivery. Clients must treat interruption/invalidation as a stale view; reconciliation and transcript replay are not implemented yet.

A prompt's reply is sent at once, while the turn's last updates may still be on their way through the service's streams or queued in the hub. So the reply names where the turn's updates end: `updatesThrough`, the agent connection's ingress sequence of the last update `ACPClient` passed on before the reply came in. `SessionModel` ends the turn only once that update is in, so a turn is never shown finished, or announced, without its last words. An error reply says nothing of where the updates end, so a failed turn's last words can still follow "Prompt failed".

- `LatchAgentXPCClient` is the reusable client side: correlated requests, `LatchAgentFailure` surfaced as thrown errors, and a single-consumer event stream that finishes on interruption, invalidation, or an out-of-sequence event.
- `LatchAgentXPCHost` is the reusable listener delegate: it owns the service, adapter, and hub, runs a synchronous admission check, applies an optional code-signing requirement before resuming a peer, and shuts everything down on request.

The XCTest XPC tests use anonymous listeners within the test process. A mocked ACP lifecycle test verifies launch, session creation, progress events, listing during an active prompt, cancellation on the same XPC connection, and shutdown. Additional tests cover ordered multi-client delivery, reconnecting after all clients leave, slow-client isolation, oversized events, abortive teardown, a client/host round trip including a brokered permission, and rejection of unauthorized peers. A separate bundled-service probe validates cross-process XPC (below), and the application bundle test exercises the real embedded service. A Mach-service host and `SMAppService` registration are not implemented yet. A reply-encoding failure can occur after a command executes, so clients must not blindly retry mutations.


## Shared session layer

`Packages/LatchSessionKit` holds everything a session does that is not drawing it, for both apps. It builds for macOS 15 and iOS 18 with Foundation, a few system libraries and the other Latch packages, and no UI framework:

- `SessionModel`, which drives one session: connecting, prompts and turns, the permission queue, configuration pickers, the chat history and its limits, and every remote rule in [Remote sessions in the app](#remote-sessions-in-the-app), adoption included.
- The service client protocol, `AgentServiceClient`, and its events; `RemoteAgentServiceClient` and `ChannelRemoteSessionConnector`, which make a remote session's client from a saved server.
- `SessionStore` and `SavedSession`, the session library both apps write in the same format; server profiles and the `ServerStore` protocol, with `ServerProfile.Stored` for a store that keeps tokens elsewhere; workspace locations; tool-call details; the render scheduler.
- `PromptAttachment`, a platform-neutral attachment that builds the prompt's blocks and refuses what a remote agent cannot take. The Mac's `ComposerAttachment` wraps one with its thumbnail and pasteboard code; the iPhone's `ComposerImage` wraps one with a JPEG it made from a photo.

It was moved out of the Mac app so that the iPhone runs remote sessions with the same reconnection, re-attach, permission and turn handling the Mac has, not a second copy of it. What stays in the Mac app is what only the Mac has: the XPC and in-process service clients, `FileServerStore`, the wake observer that calls `probeAll()`, and AppKit. `LatchAgentCore` builds for iOS too, for the agent presets and the command parser; its runtime registry and service are compiled for macOS and Linux only.

`LatchSessionKitTestSupport` runs a real `latch-server` hub and socket layer on loopback inside a test process, for this package's tests and the Mac app's. `RemoteMockAgent`, the shell agent the iOS remote smoke writes to disk, is compiled into Debug builds only.

## Network transport

`latch-server` hosts the same `LatchAgentService` as the XPC service, behind a network layer instead of XPC. The XPC protocol, its version, and the runtime registry's semantics are unchanged. Everything a network needs on top of them lives in two places: replay, turns and idempotency in the server's hub, and reconnecting in the client library.

- `LatchRemoteProtocol` (in `LatchServiceProtocol`; macOS, iOS and Linux) defines the wire: frames, commands, responses, events, tokens, pairing strings, and the loopback and tailnet address checks the server and client share.
- `LatchAgentServer` (in `LatchAgentCore`; macOS and Linux) holds the replay hub, the socket layer, the token files and the listen policy. The `latch-server` executable is only signal setup around it.
- `LatchRemoteClient` (in `LatchServiceProtocol`; macOS and iOS, compiled out on Linux) is the Network.framework client.

### Replay hub

`RemoteRuntimeHub` is an actor and the server's only reader of the service's event stream. It knows nothing about sockets.

- **Journal.** Each event a runtime produces gets a sequence number, from 1 per runtime, and is encoded once into `RemoteEventJournal`: 8 MiB per runtime and 128 MiB overall, the oldest evicted first, the newest always kept. Every frame that carries an event splices those bytes rather than encoding it again.
- **Joined chunks.** `latch-server` holds an agent's text chunk for 50 ms and joins the chunks of the same message that follow, differing in nothing but their text, into one event carrying the latest one's ACP sequence; anything else the runtime publishes goes out after the text held before it. Agents stream a few characters per chunk inside an envelope of a few hundred bytes, so a Claude Code reply journals about half as many chunk events, and the journal keeps that much more of a long session. The hub's own default is zero, which journals each chunk.
- **Cursors.** A connection attaches to a runtime from a sequence (`attach` with `after`, 0 for the start). Its writer pulls ready-to-write lines from the journal as its socket drains, so the journal is the only queue: there is no per-connection queue, a slow or returning client costs no extra memory, and no client is disconnected for being slow.
- **Gaps.** A cursor that falls behind eviction learns it once: the `attached` reply says `truncated`, or the next event frame carries `"gap":true`. Sequences only increase, but a client may see gaps.
- **Omitted events.** An event whose encoding is larger than 8 MiB, which leaves room in the frame for its envelope, is journaled as `omitted`, with its kind and size, so the cursor still moves past it. A permission request that large is journaled as its summary instead, so it can still be answered: the tool call's ID, kind, status and a shortened title, and the options.
- **Load replay.** While `session/load` runs, the agent's updates are held, up to the journal's budget for one runtime, the oldest dropped first. Once it replies, updates up to the reply's ACP sequence, and late arrivals up to it, are journaled as history: `sessionUpdate` events marked `"replay":true`, before what followed the reply; one too large for a frame is left out rather than journaled as `omitted`, and costs the held history nothing. History reaches the hub through several streams and the reply through none, so until an update from the frame before the reply or later arrives, or a second passes, what the hub itself publishes for the runtime, such as a prompt's `turnStarted`, waits, and history never follows it. The first user message of the history titles the runtime. The client that loaded the session already shows that history and skips them, as does any client with a transcript of its own; clients from before the mark skip them by the record's `loadedThrough`. A device that adopts the runtime, with no transcript, attaches from the start and shows them as the conversation so far, the user's messages included.
- **Records.** The `attached` reply carries what a returning client needs: the initialize and session replies, the latest configuration, mode, model, command and plan updates, the results of set-* commands, the active turn and the last 64 turns, the pending permission requests and questions, and the last sequence. A record goes in one frame, so past 4 MiB of pending requests the rest go as summaries. The writer activates an attachment only after writing that reply, so no event of the runtime can precede it.
- **Listings.** `listRuntimes` summarises each runtime: its agent, what was launched, the workspace, its lifecycle, the active turn, how many requests are pending, and the last sequence. It is titled by the first prompt with text, cut to its first line, with whitespace collapsed, and to 80 characters, so a device that did not start a runtime can name it; for a runtime that loaded a session, the first user message of the replayed history titles it instead. The title and what was launched are optional keys, left out when unset, so older clients and servers ignore them.
- **Idempotent commands.** Every command can be sent again after a reconnect without running twice. A prompt carries a turn ID; it is accepted at once, its outcome arrives later as `turnEnded`, and a known turn ID is accepted again without running. A launch with the same runtime ID, agent and workspace returns the running agent. `newSession`, and `loadSession` with the same session ID, on a bound runtime return the recorded reply. Stopping an unknown or exited runtime, and cancelling when no turn runs, succeed. A permission answer for a request that is no longer pending fails with `permissionRequestNotFound`, which the client counts as done. `steer` carries a steer ID: the server answers a known one with what became of it, and one sent again while the first is still with the agent waits for that one; a steer that went in is journaled as `promptSteered` where it did, and every client shows it from there. `listSessions` only reads. `forkSession` carries a fork ID, and the server answers a known one, among a runtime's last sixteen, with the fork it already made. One turn runs at a time; a second prompt gets `busy`, so a message written while the agent works waits in `SessionModel.queuedPrompts` on the client and goes when the turn ends; Stop, or anything that moves the session on, gives what is waiting back to the composer rather than sending it into whatever comes next.
- **Turn ends.** A prompt's reply reaches the hub through no stream, and the turn's updates through several, so the reply's `updatesThrough` says which update must be journaled first. Until it is, the turn stays active: the record shows it running, a cancel has nothing left to cancel, and another prompt gets `busy`. Then `turnEnded` follows the turn's last update. A second without that update ends the turn anyway, and a stop meanwhile ends it as the agent answered rather than with `runtimeExited`. An error reply carries no such position, so a failed turn's last updates can still follow its `turnEnded`.
- **Closing a connection never cancels work.** Turns, permission waits and service calls run in tasks of their own; only the reply to a gone connection is dropped.
- **Exits.** When an agent exits or is stopped, an active turn ends with `runtimeExited`, each pending request gets `permissionClosed`, and `exited` is the runtime's last event. The last eight exited runtimes stay attachable, and their IDs cannot be reused meanwhile. A crash keeps its journal; a stop keeps only those closing events.
- **Reaper.** Once a minute, a runtime with no turn and no attached connection for `--detached-timeout` (24 hours by default), or whose turn waits on a permission request with no attached connection for seven days, is stopped and forgotten, so a client that returns gets `runtimeNotFound` and resumes the session instead. A turn that waits on nothing is never stopped.
- **Launching.** The network never carries a launch profile or an environment. A launch that fails is logged with the command run and why, since the client hears only that the agent command failed. A preset or a custom command is resolved against the server's own environment, the workspace must be an absolute or `~/` path to a folder on the server, and failures come back typed: `executableNotFound`, `nodeMissing`, `workspaceNotFound`, `unknownPreset`. Commands are dispatched with an exhaustive `switch`, so a new command does not compile until its network policy is decided. Agent stderr is never journaled or sent.

### Socket layer

`RemoteServer` does blocking POSIX I/O on threads of its own, never inside a task: one accept thread per listening address, and per connection a reader thread and, once it has authenticated, a writer thread. Reader and writer threads get 1 MiB stacks, and the Linux executable asks for 8 MiB default stacks, because decoding a few KB of deeply nested JSON overflowed musl's 128 KiB default.

- **Before authentication** the server sends nothing. It reads one line of at most 16 KiB and decodes it only as a hello, within ten seconds of accepting. It holds at most eight such connections per peer address and 64 in all; past either limit a new connection closes the oldest unauthenticated one, that peer's own when it is the peer that is over, so sockets held open without a hello cannot lock clients out. The token is compared in constant time before the version, so a client without it never learns the supported range.
- **After the welcome** each request runs as a task, at most 32 per connection; more are answered `busy`.
- **The writer** is the only thread that writes after the welcome. It writes replies and pongs first, activating an attachment right after its `attached` reply; then a batch of events, round-robin across attached runtimes; then sleeps until the hub or a reply wakes it. A client that lets 4,096 replies pile up unread is dropped.
- **Compression.** A hello may offer `compression: ["deflate"]`, and the welcome then says `deflate`: every byte the server sends after the welcome, the welcome itself and a device token in it never, is one raw DEFLATE stream for the connection's life, compressed by the writer and flushed after each write, inside WebSocket binary frames when there are any. The client sends plain. `LatchRemoteDeflater` and `LatchRemoteInflater` wrap the system's zlib, the same on the server and in the apps; the inflater refuses a read that expands past four frames' worth. Events repeat their keys and envelopes, so a Claude Code turn's 60 KB of events crossed as 10 KB.
- **Teardown** shuts the socket down, which wakes both threads, and closes the descriptor only after both have left it, so no thread can block on a reused descriptor number.
- **Heartbeats.** The client pings when it has sent nothing for 15 seconds; each side closes after three heartbeats of receiving nothing.
- **The tokens**, the server's and each device's in `devices/`, are re-read on every hello, every 15 seconds and on SIGHUP. Connections that authenticated with a token that was replaced or revoked are closed, and an unreadable file refuses every hello that would use it rather than falling back to a remembered token. A device presents its token in the hello as it would the server's, so the protocol and the apps do not tell them apart. A one-time pairing code is presented the same way; a hello that says it `exchangesPairingCode` gets the device's own token in the welcome's `deviceToken`, which `LatchRemoteRuntimeChannel` connects with from then on and `RemoteSessionConnector` saves in the server's profile in the code's place.
- **Signals.** `main` blocks SIGTERM, SIGINT and SIGHUP before any thread exists, and a `sigwait` thread handles them. SIGPIPE gets a handler that does nothing rather than `SIG_IGN`, which agents would inherit; sends use `MSG_NOSIGNAL`.

### Wire protocol

One port carries two framings. A connection whose first byte is an upper-case letter, as an HTTP method's is, is an HTTP request: if it upgrades to a WebSocket, as one forwarded by a TLS proxy such as `cloudflared` does, the payloads of its binary frames, joined, are the same stream, and where a frame ends means nothing; the server writes frames of at most 64 KiB and the client messages of at most 64 KiB, so no proxy holds much of one. Any other connection is the stream itself. The server's WebSocket is its own small RFC 6455 implementation (`ServerWebSocket`, with the SHA-1 the handshake needs), with no dependencies, on the same reader and writer threads.

Frames are newline-delimited JSON, one object per line with a string `type`, written with sorted keys and unescaped slashes: `hello`, `welcome` and `rejected` for the handshake; `request` and `reply`, correlated by `id`; `event`, carrying a runtime ID and its sequence; `ping` and `pong`. Lines are capped at 16 KiB before authentication and 8 MiB plus 64 KiB after; an oversized or empty line ends the connection.

It is built to survive version skew between a server that stays put and apps that update on their own schedule. The client offers a range of protocol versions and the server picks the highest both speak. Frame types, command, response and event kinds, failure codes and agent forms are open: an unknown one decodes to a case the reader can skip or answer, so a newer peer never makes a line undecodable. A reply or event whose body cannot be read still yields its `id` or sequence, so one bad body fails one request or advances the cursor rather than forcing a reconnect. The handshake shapes are frozen. Golden fixtures in `LatchRemoteGoldenTests` pin the JSON of every frame, command, response and event; a change there is a protocol change.

### Client library

`LatchRemoteConnection` is one session, over TCP or, through a TLS proxy, over a WebSocket with TLS (`NWProtocolWebSocket` on `NWProtocolTLS`), whose certificate the system checks for the host name. Over TLS it writes the hello once the upgrade is done. Otherwise, before writing the hello it checks where it actually connected: a loopback peer, or a tailnet peer reached through a `utun` interface from a tailnet address of this device's, unless the server's profile allows an unencrypted network. Otherwise it closes with `destinationNotAllowed` having sent nothing. It correlates replies by ID, refuses to write a frame larger than the welcome's limit, reads frames no larger than its own limit whatever the welcome offers, and pings when idle. `localhost` is connected to at `127.0.0.1`, where the server listens, never at `::1`.

`LatchRemoteRuntimeChannel` follows one runtime across connections. It reconnects with backoff from one second, doubling to thirty, each wait jittered down by up to half so clients dropped together do not return together; re-attaches from the last event it delivered; drops repeated sequences; and sends pending commands again once re-attached. A prompt is awaited until its turn ends, across any number of reconnects, and re-sent under the same turn ID if needed. These retries are safe only because each command is idempotent on the server, as listed above; they are not blind retries, and the XPC rule against retrying mutating commands still stands. Being refused, an incompatible protocol, a disallowed destination, an invalid port, or a re-attach answered with a runtime the server no longer has or a record too large to send ends the channel; anything else is retried. `detach()` waits at most a second for its reply: closing the connection drops the cursor on the server anyway. `probe()` checks the link at once, as after the Mac wakes. `reconnect(using:)` points a channel that has not failed at the server another way, such as a new address or token, and connects at once; the cursor, commands waiting for a reply and turns being awaited carry over, and commands are sent again as after any reconnect.

### Remote sessions in the app

A session's location, on this Mac or on a server, decides its service client. A local session gets `LatchAgentXPCClient`; a remote one gets a `RemoteAgentServiceClient` from `ChannelRemoteSessionConnector`, which cannot reach this Mac's service or run a command here. The remote client keeps the XPC client's contract, so `SessionModel` drives both the same way: a prompt is one long request that ends when its turn ends, and the event stream ends only when the session can no longer reach its runtime. Underneath, each runtime is followed by one `LatchRemoteRuntimeChannel`, and nothing in the app retries a command itself.

- **Sequences.** Remote events carry their journal sequence, and the model records the last one it applied. Model and mode changes made by another client go through the same sequence checks as the session's own, and a turn another client started appears as its user message. A session that was idle follows such a turn to its end, with Working and Stop, rather than offer a prompt the server would refuse as `busy`; turns in an attach's backlog are not followed again. Output the server could not keep leaves one line in the transcript saying so, unless all it lost was replayed history the transcript already shows, whether the loss shows as a gap or as a truncated attach.
- **Turn ends.** A turn's outcome reaches the session apart from its events. The channel learns of the end as it delivers the `turnEnded` event, or from an attach's record, and records how far it had delivered events then. The session ends the turn only once it has applied events that far, in the step that applies the last of them, so the turn is announced with everything the server journaled before its end, and anything after it, such as another client's prompt, comes after the end. Meanwhile Stop has nothing left to stop.
- **Adopting.** `SessionModel.adopt(runtimeID:)` takes up a runtime another device started, into an empty session, and replays its journal from the start, a load's replayed history included. A runtime whose session is still being created or loaded has no record of it yet, so the adoption attaches again until it has, for up to about a minute. The binding it saves remembers that its transcript came that way, so a re-attach after a lost link or a relaunch goes on showing replayed history the journal had not delivered yet.
- **The link.** A lost link changes the banner and nothing else: the turn, the runtime and any permission sheet wait for it. A runtime's first connection fails if the server has not answered within 15 seconds, since a wrong address is for Settings to fix, not to wait out. Being refused, a disallowed destination or a protocol mismatch ends the client with a message naming the server, and the session keeps its binding, so Retry or a fix in Settings attaches again. After the Mac wakes, and when the iOS app becomes active, every link is probed at once. A launch in a folder the server does not have fails as its own error, whose advice is to start a new session in a folder that exists, since Retry never fixes it.
- **Settings.** When a saved server changes how it is reached, each client on it re-points its channel in place with `reconnect(using:)`. A session whose channel had already failed attaches again with the new settings; if it then finds its runtime gone, it stops at "Agent stopped" rather than launching an agent unasked on what may now be another machine. A rename changes only names.
- **Quitting detaches.** `SessionModel.detach()` lets go of the runtime without stopping it or answering its pending permission requests. The session's `RemoteBinding`, saved with it in `sessions.json`, holds the runtime ID, the last sequence applied, and the prompt and turn it was in. It is part of every save, not only the last, so an app that is killed leaves one too. While a turn runs, the binding points at the turn's start, and an attach cuts the transcript back to the turn's prompt and replays the turn, because a restored transcript never merges later output into an earlier message. If the replay is interrupted by a gap before it reaches what the transcript had, the saved output is put back, and only output lost beyond it is reported. Quitting stops or detaches every session at once, so it waits for the slowest rather than for all of them in turn.
- **Relaunching attaches.** `restoreSessions` attaches every session with a binding in the background, before any is selected. The `attached` record rebuilds the session, its configuration, commands and image support; the backlog replays from the binding; pending permission requests are raised; a turn still running is followed to its end, and the turn the session left running, if it ended meanwhile, is announced like any other. If the server no longer has the runtime, the session launches the agent again and resumes its saved session, with a notice when a turn's output was lost; if the agent exited, its last output and exit are shown.
- **Closing stops.** Closing a remote session stops its runtime, waiting up to ten seconds for the server before leaving it to the idle reaper, and undoing the close resumes the agent's session rather than attaching.

### Linux process spawner

On Linux, agents are not started with `Foundation.Process`. `LinuxChildProcess` uses `posix_spawn` instead, for three reasons found on Linux:

- Foundation notices a child's exit through a socket every descendant inherits, so an agent with a background tool child was reported gone only when that child exited. A thread per agent waits in `waitpid` instead.
- Foundation spawns with the calling thread's signal mask, and Swift concurrency threads block SIGTERM, SIGINT and SIGHUP, so agents never received a stop; and any spawn passes on signals the parent ignores. The spawner gives the agent an empty signal mask and default dispositions for every catchable signal.
- Foundation's pipes are not close-on-exec, so concurrent agents inherited each other's. The spawner creates its pipes close-on-exec under one lock, and the agent inherits only its standard streams.

The agent leads a new process group, and its working directory is set in the child (`posix_spawn_file_actions_addchdir_np`, which needs glibc 2.29 or musl). Reader threads stream stdout and stderr and finish at EOF, or a second after exit if a stray child still holds the pipe; after the agent exits, its group gets SIGTERM, then SIGKILL a second later. Stdin writes run on a queue of their own. macOS keeps `Foundation.Process`, with two fixes shared with Linux: stopping signals the whole process group, and a write to an agent that closed its stdin throws rather than raising SIGPIPE.

## The iOS app

`Apps/LatchiOS` is the iPhone and iPad app: `Latch.xcodeproj` with one app target, `Latch`, and the `LatchiOSUI` library in the app's package, which holds everything but a small entry point, as on the Mac. It is UIKit only, for iOS and iPadOS 18 and later, with one window scene, and registers the `latch` URL scheme for pairing links. It never runs an agent: every session is remote, and reaches its server through `LatchSessionKit`. [Latch for iPhone and iPad](ios.md) describes it from the user's side.

- **The root** is a two-column `UISplitViewController`: the sessions list in the primary column and the open session in the secondary. On iPhone, and in compact width on iPad, it collapses into one navigation stack; collapsing keeps an open session on top, and expanding selects it in the list again. `LatchAppDelegate.buildMenu(with:)` lists the app's commands in the iPadOS menu bar, and in the ⌘ list before iPadOS 26; each is a selector the responder chain answers, so one that does not apply is dimmed, and the root's `target(forAction:withSender:)` sends the session commands to the open session's screen even while the list has the focus. No controller defines key commands of its own, apart from the composer's text view, for Return, the arrows, Tab and Escape, and the permission sheet, for Escape. A session made anew under the same ID, as when its server's token is entered again, gets a new screen in the secondary column in place of the old one, whether or not the old one was on screen.
- **Servers.** `KeychainServerStore` saves profiles without their tokens (`ServerProfile.Stored`) in `Application Support/Latch/servers.json`, mode 0600, and each token in the Keychain as a generic password, service `dev.latchapp.ios.server`, account the server's ID, accessible after first unlock on this device only. A profile whose token cannot be read, as after a backup restored onto another device, stays in the file and is offered for its token again under the same ID, so its sessions come back. Each read of the file removes the Keychain items it does not name, all of them when there is no file, since items outlive a deleted app; a file that cannot be read removes none. Unlike the Mac's ad-hoc-signed app, the iOS app keeps a signing identity across updates, so the Keychain never asks again. A build without the keychain access group stops at launch rather than keep tokens anywhere else.
- **Sessions.** `SessionLibrary` owns every `PhoneSession`: a `SessionModel` plus what the list shows and the library saves beside it, the title, which a rename changes on this device only, draft, agent, folder and unread mark. It saves through `SessionStore` in the same format as the Mac, throttled while sessions change and at once, under a background task, when the scene goes to the background. At launch it restores them and re-attaches those that left a runtime on a server before any is opened. It raises attention for sessions not on screen while the scene is active, and counts approvals for the badge.
- **What the app remembers about servers.** `ServerMemory` keeps, in the app's defaults and by address, each saved server's home folder, from every handshake with one: Test Connection, New Session, the Servers checks and each runtimes listing. A server only being tried, as from a pairing link, leaves nothing. With it, paths on that server are shown as `~/…`, and a `~/…` typed in New Session is written out in full on Create, so saved sessions keep absolute paths. While the home is not known, the tilde goes to the server to resolve, a bare `~` as `~/`, which is what it accepts. It also keeps the name and address of each removed server. A removed server's sessions stay in the library under their old server ID, and when a server is added at the same address, `SessionLibrary.move(_:to:)` remakes them on the new one, re-attaching those that left a runtime there.
- **Listing and adopting.** The library asks each server for `listRuntimes` over one short connection when the list appears, on pull to refresh and when the app becomes active, and offers the runtimes that are ready and that no session here follows. Adopting one makes a session that calls `SessionModel.adopt(runtimeID:)`, attaching from sequence 0, so the journal replays from the start, a load's replayed history included; once the record arrives it takes the agent and folder the record names. An adopted agent that `AgentPreset` cannot name is kept for this run only, and is never launched blind.
- **The foreground probe.** iOS suspends the app and its sockets go quietly. Backgrounding saves and detaches nothing. When the scene becomes active, the library calls the connector's `probeAll()`, so every channel checks its link at once and re-attaches from its cursor rather than waiting for a heartbeat; lists every server's runtimes again; and reloads the Keychain if a token was unreadable before the first unlock.
- **The session screen.** `SessionDetailViewController` shows one session: a transcript, a composer pinned above the keyboard, a banner for the link and failures, a menu for the agent's settings, and the permission sheet. It connects, stops and saves nothing itself; those go back through its context's closures to the session, the library and the root. The transcript is a `UICollectionView` keyed by message, so a streaming update reconfigures one row; updates are coalesced to 50 ms. Replies are parsed by Foundation's `AttributedString(markdown:)` and drawn with UIKit attributes and views, cached per message and per piece, so a growing reply re-renders only its last piece. Only `http`, `https` and `mailto` links open, HTML is never rendered and nothing remote is loaded. A message's context menu comes from `TranscriptController`, and its text becomes selectable only through the menu's Select Text; the same controller supplies VoiceOver's custom rotors. `SentImageCache` keeps a JPEG of at most 256 pixels of each photo sent from this device, in Caches under the message's ID, because the shared history keeps only an attachment's name; the library deletes them when their session goes. The permission sheet is presented over whatever is on screen, waits for an alert to go first, and is taken down when the request closes.
- **Attention** is in the app only: a banner while the app is active, and the icon's badge, which asks for badge permission the first time a request waits off screen. There is no push: see [Latch for iPhone and iPad](ios.md#in-the-background).
- **Debug hooks.** `--smoke-test` checks that the root comes up; `--smoke-test-remote` drives the real screens against a real `latch-server`; `--ui-fixture <screen>` shows made-up servers and sessions for screenshots. The last two are compiled into Debug builds only. [Building and testing](building-and-testing.md#ios-app) runs them.
